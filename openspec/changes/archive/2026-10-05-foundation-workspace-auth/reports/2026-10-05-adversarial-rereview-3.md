### Verdict

**FAIL** (adversarial). R-2, R-5 and R-8 are resolved, and R-4 is resolved for visually blank names. The DNI part of R-1 is fixed, and the oracle is a faithful copy of `65eb994`. But the goal of R-1, a redaction that masks **everything** `65eb994` masked (the requirement the spec now states with a single R-3 exception), is still not met:

- **S-1 (Major)**: Argentine phones that `65eb994` masked leak when a number comes right before them, for example `calle 123 2945 451234`, `500 294 445 1234` and `dni 30123456 11 4567 8901` (the last one becomes `dni [phone] 4567 8901`). My corpus diff found 605 such cases in 67 276 structured inputs. The property test cannot see them because it never puts a number or a second token next to the token under test.
- **S-2 (Major)**: some secret values that `65eb994` masked also leak, outside the declared R-3 exception. Examples: `missing key: token: abc123secret`, and `password=Abc'123!xyz`, which keeps `'123!xyz`.

Both mechanisms date from step 15 and were not introduced by this diff. They break the step-17 spec sentence "SHALL mask every value that the `65eb994` redaction masked, with one known … exception", and the docs' claim that the property test "proves" the superset (S-3).

**Archiving is not advisable in the current state.**

### Things I attacked that held up

Listed only because each mitigates a documented risk:
- **Oracle fidelity.** The fixture is pattern-for-pattern identical to `65eb994` (`SENSITIVE_KEY_RE` is only used by `redactDetails`, so leaving it out is correct). It gave 0 output differences from the real file on 67 276 inputs.
- **DNI masking.** Every DNI form (plain 7/8 digits, dotted, spaced, hyphenated) across 86 contexts, including `digit.`, `.digit`, `-`, quotes, JSON, URLs, Windows paths, emoji, NBSP and CRLF, is masked wherever `65eb994` masked it. The one exception is a DNI glued to further digits, which belongs to the phone mechanism in S-1.
- **Numbers in JSON.** `redactDetails({ dni: 30123456 })` gives `[dni]`. `-30123456` is now masked (`65eb994` skipped it).
- **UUID hiding.** No meaningful privacy risk. PII shaped as 8-4-4-4-12 hex was not masked by `65eb994` either, and personal data right before or after a UUID (space, `=`, `;`, `-`) is masked.
- **Redaction performance.** 16 KB of glued UUIDs, of UUIDs mixed with `1234567.`, or of short segments: about 14 ms. The 200 KB performance suite stays green.
- **Blank names.** The full code-point scan found no letter or digit outside the invisible set that renders blank. All the attack characters listed in the brief are rejected as blank names.
- **R-5 hardening.** Grants, owner, `security invoker`, `search_path = ''` and the single overload survive `create or replace`. `authenticated` gets `permission denied`.
- **Checks.** `npm run typecheck` exit 0, `npm run lint` exit 0, `npm test` **365 passed** (39 files), `npm run test:db` **127 passed** (7 files, `Result: PASS`).
